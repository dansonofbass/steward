# Security review of Steward 0.1.0

Before the 0.1.0 release, Steward went through a release gate: separate reviews for security, privacy and thoughtfulness, a fourth review of the web platform, a second opinion on the PDF sandbox, and an install from the docs on a clean machine. This page sums up what touches security. The [privacy](0.1.0-privacy.md) and [thoughtfulness](0.1.0-thoughtfulness.md) summaries cover the rest.

## What was checked

A fresh reviewer read the code of the 0.1.0 tree against the [threat model](../explanations/threat-model.md), row by row:

- sign-in: passwords, passkeys, sessions, lockout and rate limits, the setup link, password reset, invites and the demo guard;
- same-origin checks, the content security policy and the other headers, and trusted proxies;
- book isolation: every route that opens a book, and who may write;
- the encryption key, backups and restore;
- the boundary between Steward and the gateway, and the gateway's own routes, pairing and Claude Code's door;
- the PDF sandbox: its system call filter, its Landlock wall, and how Steward decides where a PDF is read;
- uploads: size caps, CSV and OFX parsing, compressed files and file names;
- the supply chain: Dockerfiles, pinned images and actions, release signing, and the image scans.

A fourth reviewer looked at the web platform: the headers again, passkeys in the browser, the session cookie and sign-out.

## How

- The reviewer read the code, the docs and the evidence pack (the release images' scans, the PDF sandbox's checks in the release image, the claims ledger's own checks). Two short runs confirmed findings; nothing else was run.
- A second model read the PDF sandbox's checks and listed concrete inputs that might break them. Each was tried against the code, and two were confirmed by running them in a confined child.
- The web reviewer checked the browser code against current platform guidance for headers and passkeys.
- An agent installed Steward from the docs on a clean virtual machine and checked Get Steward ready's Secure address row on an untrusted certificate.
- Each reviewer was an AI model working alone, on its own copy of the code, with no view of the other reviews.
- Every fix was checked again by a fresh reviewer, and the PDF filter got a second pass from the second model. Those re-checks found gaps in the fixes themselves, which were closed before they merged.

## What was found

Critical means a claim is false in a way that exposes data or lets someone in; Important means a claim says more than the code does, or a check has a reachable hole with limited impact; Minor is hardening or polish.

| Severity | Count |
|---|---|
| Critical | 0 |
| Important | 6 |
| Minor | 12 |
| Not a defect | 2 |

Of these, the security review found 3 Important and 7 Minor, the second model 2 Important and 3 Minor (and 2 that didn't hold up), the web review 2 Minor, and the install 1 Important.

## What was fixed

- With email off, an invite could hand a household manager a sign-in link for someone else's existing account. Now an invite carries a link only for an account the invite itself made.
- On a kernel without Landlock, the PDF reader ran with its system call filter alone, which is less than the threat model said. Now Steward reads a PDF only when the filter and the wall are both up; otherwise the PDF goes to the gateway or waits. [S6](../CLAIMS.md#s6)
- A PDF reader taken over by a crafted file could send signals to Steward through a file descriptor setting. The filter now refuses that setting.
- The same reader could change file modes and other file details outside its folder through calls the filter didn't list. The filter now classifies every system call on x86_64, and a test fails on any it doesn't.
- One large OFX file could keep Steward busy for hours, because parse time grew with the square of its size. Parsing is now linear, and a scan of every upload parser fails on the pattern that caused it.
- Get Steward ready said the address was secure on a certificate the browser didn't trust, where passkeys can't work. It now says when this browser can't use passkeys there.

The cheap Minors went into the same fixes: a reset link now removes the account's passkeys as a manager's reset does, the reader stops when Steward stops, and the threat model and the ledger say what the lockout does. [S5](../CLAIMS.md#s5)

## What's left

These Minor findings become public issues after the release:

- Count sign-in lockouts per device and username.
- Check the Host header on the API.
- Refuse an unknown `STEWARD_ENV`.
- Add dependency update checks for the images, actions and packages.
- Verify and pull images by digest.
- Import the PDF libraries before the wall and narrow the wall to fonts.
- Passkey sign-in from the username box, and telling the device when a passkey is removed.
- More headers: Trusted Types, a permissions policy, reporting, the older framing header, and a `__Host-` cookie.

The known limits of each check, such as a taken-over PDF reader still seeing which files exist, are in the [threat model](../explanations/threat-model.md). What the privacy checks can miss is in [Privacy](../explanations/privacy.md#what-the-checks-can-miss).
