# Privacy review of Steward 0.1.0

Before the 0.1.0 release, Steward went through a release gate: separate reviews for security, privacy and thoughtfulness, a fourth review of the web platform, and an install from the docs on a clean machine, with a real question to Claude. This page sums up what touches privacy. The [security](0.1.0-security.md) and [thoughtfulness](0.1.0-thoughtfulness.md) summaries cover the rest.

## What was checked

A fresh reviewer read the code of the 0.1.0 tree:

- every path to Claude: the typed question, each lookup Claude can ask for, approved store rows, history, the warm-up request, chat titles, categorizing, statements and Claude Code;
- the gateway's checks: the exact pass over what Steward holds and the model that looks for other names;
- the sent log, by code and against a real turn's export;
- logs: Steward's, the gateway's and the HTTPS proxy's;
- what leaves the machine: Steward's own connections, telemetry, and the programs beside it (Tailscale, Ollama, the model download);
- the privacy docs and every Private claim, against the code;
- the tree and the release images, for personal strings.

A fourth reviewer looked at the web platform, including what the browser keeps after sign-out.

## How

- The reviewer read the code and the docs, and ran short checks of the functions that find names and payees to confirm findings.
- After the install, the same reviewer read its evidence: the session logs, the sent log's export from a real Ask turn, and the proxy's log on a failed search. It also read the proxy's settings and the gateway's environment inside the running containers.
- Each reviewer was an AI model working alone, on its own copy of the code, with no view of the other reviews.
- Every fix was checked again by a fresh reviewer. Those re-checks found more forms of the same over-wide claims and more log lines that could carry a name, which were fixed before merge.

## What was found

Critical means a claim is false in a way that exposes data, or a personal string is in the tree; Important means a claim says more than the code does; Minor is hardening, polish or unclear wording.

| Severity | Count |
|---|---|
| Critical | 0 |
| Important | 5 |
| Minor | 15 |

The privacy review found 1 Critical, 4 Important and 7 Minor, and 5 more Minor after the install. Triage added 1 Important and 1 Minor, and the web review found 1 Minor. The one Critical was re-rated Minor because it was the maintainer's initials, which the maintainer chose to make part of their public identity on the project. What held of it (the initials in a few comments and messages) was fixed.

## What was fixed

- The docs promised that no name reaches Claude, but a payee in an approved store row can be a person. The docs and the in-app text now say so. [P4](../CLAIMS.md#p4)
- The docs said the gateway's check catches every name. It is a model, and it can miss one; some names are dropped on purpose. The docs now say what Steward replaces, and that a model on the gateway looks for the rest and can miss one. The model's evaluation is cited. [P4](../CLAIMS.md#p4) [P11](../CLAIMS.md#p11)
- The docs overstated what the exact pass over known names matches: it matched less than everything Steward holds. They now say what it matches, and Privacy lists the misses.
- The in-app text before chat is turned on, and Settings › Chat, repeated those claims. Both are narrowed, and a test now reads the in-app text for the phrases found false.
- The HTTPS proxy's error log could carry a search from the address. The proxy's log now drops the address and its query, and the install confirmed it on a real failed search. [P10](../CLAIMS.md#p10)

The Minors fixed in the same work: Tailscale's log upload is off, the gateway turns off Hugging Face telemetry in every way it runs, log lines name a book by its id and keep a bank's error to its code and a short, cleaned message, and the claims about the sent log, approvals and Claude Code say exactly what each does. [P6](../CLAIMS.md#p6) [P7](../CLAIMS.md#p7) After the install, the sent log names the model each part went to, and the gateway guide explains a harmless tokenizer warning instead of leaving it alarming.

The install also bore out the claims it could: after a real Ask turn, a search of every log for the imported descriptions, amounts, the question, the account's name, the setup token, the pairing code and the person's name found nothing, and the sent log's export held the parts sent and no description, store name or account number.

## What's left

These Minor findings become public issues after the release:

- Mask payment-app recipients in approved store rows unless the row is ticked.
- Widen the exact pass: two-letter parts of names, people whose names are ordinary words, the start of each address, and more of the names Steward holds.
- Show the fixed instructions behind the sent log's hash in Settings › Chat.
- Observe what Ollama contacts on its own, and keep it off the internet except to pull a model.
- Drop the install's own address from the proxy's log, or say in Privacy that it's there.
- Clear the net-worth milestone the browser keeps after sign-out.

The re-check's log capture covered account creation and a first import without a container restart, which answered the review's question about lost log lines. A PDF upload wasn't repeated in it.

The gaps the checks can't close are listed in [Privacy](../explanations/privacy.md#what-the-checks-can-miss). The limits of the security checks are in the [threat model](../explanations/threat-model.md).
